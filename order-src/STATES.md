# 상태 목록 (11/16 "상태 머신 헌터")

이 앱에서 "지금 어떤 상태인가"를 정하는 것들을 한 장에 모았습니다. 예전에는 화면마다 그 자리에서 조건문으로 다시 판단해서, 한쪽만 고치면 서로 어긋날 수 있었습니다.

- 상태를 물을 땐 아래 **함수 하나**만 부릅니다. 같은 조건을 새로 쓰지 않습니다.
- 낱말이나 시간 값을 바꾸면 `node order-src/test/states.mjs [kv.json]`이 어긋난 곳을 알려 줍니다.
- 에이전트·시험은 화면 글자를 긁지 말고 `window.__orderCalc.appState()`와 `data-need` · `data-mode` · `data-phase`를 읽습니다.

## 1~4. 요청 수명과 화면 상태

요청 한 건은 시트의 한 칸에 적히고, 폰과 PC가 번갈아 고칩니다.

```
(없음) ──폰 [GW 전송]·[불러오기] 또는 collect.py──▶ pending ──확장이 집어 감──▶ running ──▶ done
                                                    │                           └──▶ error (멈춘 곳을 글로)
                                                    └─ PC가 끝내 안 집어 감 → 화면에서만 "응답 없음"(시트 값은 pending 그대로)
```

시트에는 네 낱말만 있습니다. "응답 없음"과 "PC 켜면 받아요"는 시트에 없는 **계산된 상태**라서, 시각과 PC 신호를 같이 봐야 압니다. 그 계산이 `misState()` · `salesState()`입니다.

| 화면 낱말 | 뜻 | 발주 전송 | 매출·메뉴 |
|---|---|---|---|
| `idle` | 요청 없음(또는 어제 것) | 버튼만 | 버튼만 |
| `run` | PC가 받아서 하는 중 | "입력중" | "PC가 GW·MIS 여는 중…" 등 |
| `wait` | PC가 꺼져 있어 기다림 | "PC 켜면 자동 입력" | "PC가 꺼져 있어요 · 켜지면 받아요" |
| `ok` | 끝남 | "✓ 저장 완료" | "가져옴" |
| `bad` | 오류 또는 응답 없음 | "확인 필요" · "PC 응답 없음" | 같은 뜻 |

시간 값은 세 군데(앱 · collect.py · 확장)에 있고 서로 맞아야 합니다.

| 값 | 앱 | collect.py | 확장 | 지켜야 할 것 |
|---|---|---|---|---|
| PC 켜짐으로 보는 시간 | `PC_ALIVE` 20분(예전 방식 3분) · `SP.alive` | 20분 · 3분 | 10분마다 신호 | 셋이 같고, 신호 간격보다 김 |
| 발주 전송 응답 없음 | `MIS_STALE` 기다림 7분 · 입력 중 13분 | 해당 없음 | 6분 · 12분에 스스로 끝냄 | 앱이 확장보다 김 |
| 매출 읽는 중 | `SP.runMax` 14분 | 14분 | 12분에 스스로 끝냄 | 앱 = collect.py > 확장 |
| 매출 기다림 | `SP.pendMax` 6분 | 6분 | 해당 없음 | 앱 = collect.py |
| PC 꺼져 있을 때 기다림 | `SP.offMax` 18시간 | 18시간 | 6시간까지만 집어 감 | 아래 "알려진 틈" |

**알려진 틈.** 확장은 6시간 넘은 매출 요청을 집어 가지 않는데, 앱은 18시간까지 "켜지면 받아요"라고 보여 줍니다. 그 사이(6~18시간)는 PC가 켜진 것을 본 앱이 요청을 다시 보내거나(`re` 2번까지), 10:23·15:23 자동 수집이 새로 보내서 메웁니다. 확장은 다시 설치해야 바뀌므로 이 값은 앱 쪽에서 맞춥니다.

## 5~7. 재고 칸 · 필요량 칸 · 86

- 재고 칸: `none` 빈칸 · `counted` 센 값 · `est` 앱이 채운 예상 재고. `est`는 발주 계산에는 쓰지만 채점·학습·다음 날 예상의 출발점으로는 쓰지 않습니다.
- 필요량 칸: `none` 계산 못 함 · `idle` 재고를 안 넣음(이번 기간 필요량만 회색으로) · `unknown` 재고는 있는데 계산 못 함 · `done` 발주 넣음 · `low` 앱 예상보다 적게 넣음 · `enough` 발주 안 해도 됨 · `offday` 오늘은 그 업체 발주일이 아님 · `buy` 발주필요.
- 86 모드: `counted` 오늘 센 값으로 · `est` 최근 3일 안에 센 값에서 낸 예상으로("확인필요") · `night` 영업이 끝난 뒤 내일 문 열 때 예상으로. 한 번에 쓰는 품목(`useStep`, 대두유)은 같은 모드 안에서 "쓸 횟수 × 한 번 양"으로 견줍니다.

## 화면에 그려 둔 값은 상태가 아니다 (11/16 사고)

Forecast 화면은 저장할 때 화면의 7칸을 그대로 시트에 썼다. 화면을 그린 뒤 PC가 실제 매출을 채우면 화면 칸(빈칸)과 시트 값이 달라지는데, 다른 칸을 건드리는 순간 빈칸이 시트를 덮어썼다. 지금은 **사람이 고친 칸**(그릴 때 값 `defaultValue`와 달라진 칸)만 저장한다. 입력 화면을 새로 만들 때도 같은 원칙: 화면 값을 통째로 저장하지 말고, 바뀐 칸만.

## 고칠 때

1. 상태를 묻는 조건을 새로 쓰지 말고 위 함수를 부릅니다. 낱말이 모자라면 함수에 낱말을 더하고 이 문서 표에 적습니다.
2. 시간 값은 표의 "지켜야 할 것"을 보고 양쪽을 같이 고칩니다. 확장 쪽 값은 KM이 다시 설치해야 바뀝니다.
3. `node order-src/test/states.mjs <kv.json>`을 돌립니다. 화면이 바뀌면 안 되는 정리라면 고치기 전 `order.html`과 같은 자료·같은 시각으로 열어 칸의 HTML이 같은지 봅니다.
